## Pehle seedhi baat — main kya kar sakta hoon, kya nahi

Shuru karne se pehle honest rehna zaroori hai, warna aage jaake time waste hoga:

**Main kya de sakta hoon (is chat se):**
- Poora real Kotlin/Jetpack Compose source code, phase-by-phase, Rule 1-21 apply karke
- Gradle setup, GitHub Actions CI workflow, package structure — jaisa aapke **Brain — Offline AI Engine** project mein hua tha
- Har phase ka ZIP jo aap Termux se `git push` kar sakte ho
- Design ko match karne ki poori koshish — colors, layout, panels, button placement — reference image se

**Main kya NAHI kar sakta (is environment ki limit hai, koi excuse nahi):**
- Do real phones ko is chat se connect nahi kar sakta — QR-pairing, WiFi/LAN discovery, real socket connection — yeh sab sirf **aapke Termux + real phones par hi test ho sakta hai**, mere paas na network hai na physical device
- GitHub par khud push nahi kar sakta — code taiyar karunga, push aap karoge (jaisa hamesha hota hai)
- "Working, sirf test nahin" — yeh tabhi confirm hoga jab APK aapke asli phone par chalega. Main sirf **compile-correct, logic-correct, real code** de sakta hoon (Rule 10) — asli multi-device run ka pass/fail sirf aapke test se pata chalega

Isliye jo bhi neeche "Phase Complete" likha hai, uska matlab hai *"code ready + self-reviewed"* — **"device-tested"** nahi, jab tak aap khud confirm na karo.

## Rules kaise apply hongi (Rule 8 Part B + Rule 11 — sab ek saath, automatic)

Har phase par yeh rules combined apply hongi, alag pass mein nahi:
- **Rule 9** — pehle context confirm: yeh Android app hai, Kotlin + Jetpack Compose, Termux+GitHub Actions build
- **Rule 1, 4, 5, 6, 7** — har naya function/screen ka entry→processing→endpoint chain, orphan-check
- **Rule 2, 20** — helper split jab kaam bada ho, AI-calls mein minimal-necessary-payload
- **Rule 10, 21** — likhte waqt hi syntax/logic correct, chota-function, no dead code, no infinite loop
- **Rule 12** — naya feature banane se pehle workflow design + risk-check, tabhi code
- **Rule 17** — retry/reuse waale flows (jaise multi-device retry, evaluation retry) mein endpoint sirf "bana" nahi "sahi" bhi verify hoga
- **Rule 18** — har phase shuru karne se pehle poora saved project-context (language per component: Kotlin/XML-if-any/Gradle) reload, kuch bhi ambiguous ho to guess nahi, aapse poochunga
- **Rule 19** — koi bhi existing file edit copy par pehle, clean-validate ke baad hi live file/commit
- **Rule 13, 14, 15, 16** — display/output screens ke liye cleaner-viewer helper, har fix ki weakness dobara check, chhota sub-helper, aur end mein full sequential audit

Koi fake API key, koi dummy response, koi mock data screen mein hardcoded nahi hoga — jahan bhi real backend/model chahiye (AI evaluation, workload distribution), wahan ya to real local logic hogi ya aap se real credential/model maanga jayega, kabhi silently fake nahi dikhaya jayega.

## Phase 1 — Foundation + Training Setup
**Reference image (Sections 1 & 2):**
![Phase 1](./plan-images/phase1_training_setup.png)

Kya banega:
- Project scaffold: Gradle Kotlin DSL, minSdk/targetSdk, GitHub Actions CI (Termux → push → build), package structure
- **AI Training Center** screen: skill/module checklist (real toggle state, persisted), training-level selector (Basic/Intermediate/Advanced), Add Examples / Add Project (ZIP) real file picker

Rules focus: Rule 1 (entry se endpoint), Rule 12 (progress engine ka design pehle), Rule 21 (chota function, no dead loop in the training loop).

## Phase 2 — Multi Phone Connect + Workload Distribution
**Reference image (Sections 3 & 4):**
![Phase 2](./plan-images/phase2_multiphone_workload.png)

Kya banega:
- **Phone 1 (Master)**: real QR code generation (Device ID + Local IP encoded), connection-process state machine (Scan/Pair → Authenticate → Exchange Keys → Capabilities → Connected)
- **Other Phones (Worker)**: real QR scanner (camera permission) + manual code entry fallback, "Connect" action that performs a real LAN handshake
- **Workload Distribute** panel: real device-capability-based split (not a hardcoded 20/30/25/25 pie) — percentages computed from each connected device's reported CPU/RAM/battery
- Training Sync: real gradient/update exchange step (or, if full distributed training is out of scope for v1, an honestly-labeled "sync placeholder" that we flag to you rather than fake-animate)

⚠️ Yeh sabse risky phase hai — real device-to-device networking. **Yahan Rule 18 se ek cheez zaroor confirm karni hogi aapse: connection kaunse transport se ho (same-WiFi LAN socket, ya WiFi Direct, ya Bluetooth)?** Yeh guess nahi karunga.

Rules focus: Rule 9 (platform/transport context), Rule 17 (retry-connect ka result sirf "connected dikha" nahi, genuinely connected hona chahiye), Rule 2 (connect/retry helper split).

## Phase 3 — Evaluation Lab
**Reference image (Section 5):**
![Phase 3](./plan-images/phase3_evaluation_lab.png)

Kya banega:
- Evaluation-mode picker (Build from Scratch / Feature Add / Fix Bugs / Analyze / Explain / Best-Practice Check)
- Task creation form (instruction, stack, difficulty, time limit) — real form state
- **AI Working Process** 9-step pipeline (Intent → Plan → Files → Code → UI → Build → Test → Fix → Final) — each step a real pipeline stage calling your configured AI engine (Brain's local API, or whichever engine you point it to — never hardcoded fake output)
- Output Preview — real rendered chat/app-preview of what the pipeline produced
- Evaluation Score panel — scores computed from actual real test/lint/build results, not randomized numbers

Rules focus: Rule 20 (minimal-necessary-payload jab task/engine ko bheja jaye), Rule 13 (output preview ek cleaner-viewer helper se dikhega, raw dump nahi), Rule 17 (score sirf tab "sahi" jab correctness verified ho, sirf "ban gaya" nahi).

## Phase 4 — ZIP Project Testing
**Reference image (Section 6):**
![Phase 4](./plan-images/phase4_zip_testing.png)

Kya banega:
- Real ZIP upload + extract, project read/analyze, dependency install, build/run — using real toolchain calls (not simulated pass/fail)
- Errors & Issues identify → Fix Automatically → Rebuild & Test → Verify Fixes — this literally reuses **your own Rules 1-21 methodology** as the fix-engine's internal checklist (Rule 5/6/7 orphan-check, Rule 10 correctness, Rule 19 copy-then-validate-then-writeback)
- Problems & Fixes list, Diff/Changes view, Result Summary — all generated from the real diff between original ZIP and fixed ZIP
- Download Fixed ZIP / View Full Report — real file output, not a static mock

Rules focus: this whole phase IS Rule 19 (copy-edit-validate-writeback) and Rule 5/6/7 (orphan/dead-code judgment) applied as product features, plus Rule 13 for the diff/report viewer.
